# Daemon protocol

`@moonbase/daemon-protocol` is the daemon's wire protocol, shared by the daemon and every client: the signed health route, the HMAC-framed WebSocket, its server, and the client-side services over it. It needs no chat engine: the server receives chat and daemon operations as injected `ChatClient` and `DaemonClient` handlers, and clients get the contracts services back.

| Export | Role |
| --- | --- |
| `./server` | `serveChat(config, client, daemon?, capabilities?, socket?)`: the daemon's 127.0.0.1 listener in either mode, serving the WebSocket at `/v2/socket` and signed health at `/v1/health`; `socket` adds provider setup change notifications and connection tracking (`sources`), a test clock, `admit` (called for each request and authenticated health probe: it refuses by throwing, or returns what ends the admission once the answer settles, even after the connection closes) and `workspace`, an injected `WorkspaceHostClient` (the server cannot import the workspace); `makeDaemonClient(runtime)` binds its folder, control and provider setup services, `makeWorkspaceClient(host)` binds a file host's `WorkspaceHostServiceShape` (its operations and its watch), and `localDaemonCapabilities` / `hostDaemonCapabilities` are what each mode advertises |
| `./remote` | `RemoteChatLive`, `RemoteLocalHostLive`, `RemoteProviderSetupLive({host, openUrl, sameMachine})` and `RemoteWorkspaceHostLive({host})` (the file host's `WorkspaceHostService`): client-side services over an injected `ConnectionService`, sharing one WebSocket per connection generation when built together |
| `./socket` | `connectDaemonSocket(endpoint)`: one authenticated WebSocket to a daemon that advertises `socket-v1`, for requests and subscriptions; the `./remote` services use it |
| `./folders` | Host-side folder authority, for the daemon only: `createFolderApprovals(file)`: approved working folders, re-checked by identity on use; `createRootFolders(roots, { reserved })`: a host-mode daemon's approved roots and the folders under them, refusing a root that holds or sits in a `reserved` path. Both return the contracts `FolderApprovals`; `withCheckoutFolders(folders, checkouts)` widens a local daemon's `has` to the roots of the workspace's approved checkouts (picker approvals, `approve` and the recent list are unchanged) |
| `./health` | The signed health check: `checkHostHealth(endpoint)` (the client side, which `LoopbackConnectionLive` uses and consumers inject into `SshLive`), `createHostHealthReply` (the server side) and `validateHostHealth`; HMAC-SHA256 proofs under `moonbase-daemon-health-v1` in both directions, over the host's identity, protocol version, version and capabilities. It fails with the contracts `HostVerificationError` |
| `./loopback` | `LoopbackConnectionLive({directory})`: privileged `ConnectionService` for a daemon on this machine |

Remote hosts run the [daemon](../../apps/daemon/README.md#remote-host) in host mode, reached through the [SSH package](../ssh/README.md); its listener binds only `127.0.0.1`.

## Behavior worth knowing

- Clients reach a daemon only over its WebSocket, whose messages are HMAC-authenticated; over SSH, OpenSSH provides transport encryption. The protocol is version 2; signed health (`GET /v1/health`, HMAC-SHA256 under `moonbase-daemon-health-v1`) is the only other route, used to verify a host before connecting. Protocol 1 hosts and clients are refused.
- Signed health lists capabilities. Every host has `chat-v0`. A server given `daemon` operations (the daemon, in either mode) adds `daemon-local-v1` (local-mode chats, `getActiveWork`, `markFolderAsProject`), `providers-v1` (provider setup) and `folders-v1` (`approveFolder`, `listRecentFolders`, `checkChatFolder`, `checkApprovedFolder`); a host-mode daemon adds `roots-v1` (`listHostFolders`). Every daemon advertises `socket-v1`; one given a `workspace` client adds `workspace-v1`. The server serves only operations whose capability it advertises. The client checks the capability in the welcome's signed health before sending, so nothing reaches a host that doesn't advertise what it needs: from a host without `daemon-local-v1`, `getChatHost`, `createChat` and every daemon operation are `Incompatible`, since every host must be a daemon.
- Daemon operations are strictly decoded where they arrive and listed in explicit handler maps; their inputs name the host, which the server checks. Provider setup is scoped to an owner the client names (Electron uses its document id), so one owner never sees or answers another's flow; `releaseProviderOwner` ends an owner. The mutations (`approveFolder`, `markFolderAsProject`, provider login, answer, cancel and logout) carry request IDs echoed in their replies: a lost or unproved reply is `Uncertain` and is never resent, and the server returns a recent request's outcome (keyed by owner and request ID) again rather than rerunning it. Only a refusal the daemon made before applying anything (`InvalidInput`, `Unauthorized`, `Incompatible` or `Conflict`) is forgotten, so it may be sent again.
- The WebSocket (`/v2/socket`, on the same 127.0.0.1 listener) refuses an upgrade with an `Origin` header (any browser page) or a `Host` other than `127.0.0.1:<any port>` (through an SSH forward it names the client's end of the tunnel), and allows 32 authenticated connections plus 8 still waiting for their hello; a ninth waiting one closes the oldest, so a held handshake occupies a slot only until newer ones arrive. Authenticated connections are unaffected, but a fast local flood of upgrades can still delay or refuse a new client's handshake. The hello must arrive within 5 s of the challenge, and the client allows 20 s from connecting to the welcome so a slow SSH forward still connects. The hello is the only frame accepted before it (a ping is refused); a wrong token, host or protocol, and any tampered, replayed, reordered, missing, reflected, unmasked, text, fragmented or oversized frame (over 256 KiB; 4 KiB before the hello; refused from its header) closes the connection with code 1008 and no reason. Requests are decoded strictly, share the daemon's request memory and are held to `maximumChatRequestBytes`, at most 32 in flight (a 33rd is refused `Unavailable`, not queued) and 64 chat or daemon replies or refusals waiting to be written. Every request gets exactly one reply: a cancelled read is aborted, leaves the 32 at once and is answered `Cancelled` (a reply queued but not yet started is dropped for it); a mutation is never cancelled; closing the connection cancels its reads but lets mutations finish, so a client retries with the original request ID, and the client fails a mutation whose reply was lost as `Uncertain` and never resends it.
- Subscriptions (64 per connection) number their updates. The server keeps only the latest unsent value of each and works out the update when it can write: a delta from what it last sent where one pays (the running response's appended text and replaced parts, chat-list rows, provider fields, at most 32 KiB), else a fresh snapshot, so a slow client gets fewer, coalesced updates and never a backlog. Replies go before updates, so streaming never holds up Send or Stop. While the socket holds 1 MiB the server stops writing and reading, pongs included; a client that reads nothing of it for 20 s is disconnected. Chat updates come from the chat watch, which is driven by Pi Durable's commit invalidation; the chat list (`ChatService.watchChatList`: its first page, and the chats past it that changed while watching, at most 32 and within 256 KiB, the least recently changed let go and counted as `dropped`) is read again after commits that change conversations, tasks, metadata or a run's start or end, re-reading only the changed chats past the page, and provider setup (the daemon's `getProviders` for the subscription's owner) after each flow or sign-in change that `sources.subscribeProviderSetup` reports (the daemon wires `ProviderSetupChanges` to it); `ProviderSetupLive`'s `watch` follows changes the same way in process. A subscription outlives its connection for 60 s (64 in all) with its last 64 deltas (256 KiB, and 16 MiB across all subscriptions, the oldest subscriptions' going first): subscribing again with its ID and `afterSequence` replays the deltas after it, or resets with a snapshot when they are gone (a chat list always resets, since its source restarts without the chats that changed past its page meanwhile). A client marks only a snapshot that arrives first after such a resubscription as `reset`. One client's identical chat list and provider setup subscriptions share one socket subscription. Subscribing with an ID another connection holds takes it over, and the old connection gets a `Conflict` error update for it. Besides kept deltas, each subscription holds the value it last sent and at most one unsent value, each a snapshot of at most 256 KiB. Each side sends a heartbeat after 10 s without sending and closes after 30 s without receiving an authenticated message (WebSocket pings are answered but do not count); these are separate from request deadlines.
- A refused daemon operation's signed error may name a reason from `daemonErrorReasons` (`@moonbase/contracts/daemon`), such as Claude Code managing its own sign-in or a missing folder; the client shows its own fixed message for that reason and code, and a generic one otherwise, never the host's text.
- `LoopbackConnectionLive` takes the expected host and store from the daemon's `identity.json` when it is built, and starts disconnected, so it builds while the daemon is stopped (without `identity.json` it fails `Unavailable`). On each connect it reads `identity.json`, `endpoint.json` and `token` again (private files in a private directory, never followed through links) and verifies signed health for that host and store. A connect that finds the same daemon process (the port and `pid` in `endpoint.json`) keeps its generation; a restarted or replaced one starts a new generation, even on the same port, and requests bound to the old one fail. It is privileged: its endpoint holds the token, so it never reaches a renderer.
- The `./remote` services built together share one WebSocket per connection generation, opened on first use and again after it closes; a socket of an older generation is closed. A request is sent once: one whose reply is lost, takes longer than 20 s or arrives after the connection's generation changed is `Unavailable`, or `Uncertain` for a mutation. A subscription whose connection drops reconnects after 250, 500 and 1000 ms per outage (an authenticated message at least 5 s after its connection's first update renews that budget) and resumes with `afterSequence`; meanwhile a chat watch shows its last snapshot as `reconnecting`, and a chat list update that came as a fresh snapshot after missed ones is marked `reset`. It fails `Unavailable` once the budget is spent or the connection's generation changes, and with the daemon's code when the daemon ends it.
- **Workspace (`workspace-v1`).** The file host's operations (`HostCommand`, with the workspace's inputs, plus `saveStatus`, `acknowledgeSave` and `listOperations`) are served only when health advertises the capability, and each input's checkout must name this host (`Unauthorized` otherwise). Reads are cancellable; `isHostMutation` lists the mutations (`saveFile`, `mutate`, `createWorktree`, `initializeRepository`, `acknowledgeOperation`, `acknowledgeSave`, `createChatWorktree`, `turnChatIntoProject`, `captureImports`), which run to completion even if the connection closes, are not remembered by the server and, when their reply is lost, are `Uncertain` and never sent again. The host replays a recorded success or deterministic refusal for the same request ID; after `Unavailable`, `Cancelled` or `Persistence` the same ID runs again; after `Uncertain` it is reported interrupted, so a client mints a new ID once the leftovers are inspected. `captureImports` is not journalled. A workspace request whose JSON exceeds a frame is sent at once as back-to-back `requestChunk` messages (128 KiB of raw bytes each, its own sequence-numbered HMAC frame), up to 16 MiB. One that would take a connection's chunked input in flight past 32 MiB is read, checked and discarded, and refused `Unavailable` before it runs. Any gap, overlap, replay, tampering, oversized or non-canonical chunk, total over the bound, other message between one request's chunks, chunked chat request, or chunk to a host without the capability closes the connection with 1008. A reply is encoded once, up to 16 MiB (a larger one is replaced by an `InvalidInput` refusal, or `Uncertain` for a mutation, which applied); workspace replies are written in order, one chunk of the first at a time between chat replies and updates, so a large read never stalls chat streaming. While 64 MiB of them wait to be written, further workspace requests are refused `Unavailable`; the client's reassembly allows one workspace reply plus the chat payloads beside it. Workspace failures cross the wire as a code plus fixed text only. Deadlines are the client's, by class (`hostDeadlineMs`): reads 20 s, lookup and search 30 s, mutations 60 s, worktree creation (chat worktrees included) and `git init` 120 s; past one a read is cancelled and a mutation is `Uncertain`, which `saveStatus` or `operationStatus` resolves. `RemoteWorkspaceHostLive` keeps at most 16 workspace requests in flight, plus 2 that only `saveStatus` and `operationStatus` use, so chat keeps at least 14 of the server's 32 and the status calls always have a place; a request waits up to its deadline for a place (`Unavailable`, never sent, past it) and keeps it until the daemon has answered it (a cancel included) or the connection closes. It refuses an input for another host, and a reply naming a checkout of another host (`Incompatible`, or `Uncertain` for a mutation). The `workspace` subscription (target `{checkout}`, at most 64 per connection apart from the 64 others) has the value `{ready, revision, error?}`, `revision` rising with every change the host's watch reports; a host watch that fails ends it with its code, and one that finishes with `Unavailable`. Values are sent whole, and workspace subscriptions are not kept to resume: one subscribed again starts from a fresh snapshot, which `RemoteWorkspaceHostLive.watch` delivers as an event to refresh from (it ignores `paths`: the whole checkout is followed). Only the value that first says the watch is ready becomes a `ready` event.
- Each value is decoded once, where it arrives: the server decodes request inputs and the client decodes replies (chat replies with `checkChatOutput` from `@moonbase/contracts/chat-validation`). The services on either side, and `serveChat`'s configuration, are typed and trusted.

## Checks

```sh
bun run --cwd packages/daemon-protocol typecheck
bun run --cwd packages/daemon-protocol lint
bun run --cwd packages/daemon-protocol test
```

`test` runs under `bun test` against the real chat engine (`@moonbase/chat-runtime`, a dev dependency) with controlled providers and temporary stores. One case runs the compiled remote client in the pinned Electron, as desktop main runs it, which covers the client's Node path and that it bundles no engine. Host-process tests run a controlled local-mode host (`test/faux-host.mjs`) as a child process: crash recovery and parked work.
