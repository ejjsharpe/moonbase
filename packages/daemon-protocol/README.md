# Daemon protocol

`@moonbase/daemon-protocol` is the daemon's wire protocol, shared by the daemon and every client: the signed health route, Effect RPC for chat, folders, control and provider setup (`/v3/rpc`), the workspace's own Effect RPC socket (`/v3/workspace`), their server, and the client-side services over them. It needs no chat engine or file host: the server receives the chat, folder, provider setup and file host services, and clients get the contracts services back. Folder approval policy belongs to the [daemon](../../apps/daemon/README.md).

| Export | Role |
| --- | --- |
| `./server` | `serveChat(config, services, options?)`: the daemon's 127.0.0.1 listener in either mode, serving RPC at `/v3/rpc`, signed health at `/v1/health` and, given `options.workspace` (a file host's `WorkspaceHostServiceShape`), the workspace socket at `/v3/workspace`; `options.admit` is called for each request, watch and authenticated health probe (it refuses by throwing, or returns what ends the admission once the answer settles, even after the connection closes) and `options.trackWorkspaceConnection` while each workspace connection is open; `localDaemonCapabilities` / `hostDaemonCapabilities` are what each mode advertises |
| `./remote` | `RemoteDaemonLive({host, openUrl, sameMachine})`: chat, folder and provider setup services over one RPC link to a host's daemon (`DaemonRpcLinkLive`), built from `RemoteChatLive`, `RemoteLocalHostLive` and `RemoteProviderSetupLive`; `RemoteWorkspaceHostLive({host})`: the file host's `WorkspaceHostService` over the workspace socket; `EndpointConnectionLive(endpoint)`, a `ConnectionService` for one known endpoint (tests and scripts on the daemon's machine) |
| `./health` | The signed health check: `checkHostHealth(endpoint)` (the client side, which `LoopbackConnectionLive` uses and consumers inject into `SshLive`), `createHostHealthReply` (the server side) and `validateHostHealth`; HMAC-SHA256 proofs under `moonbase-daemon-health-v1` in both directions, over the host's identity, protocol version, version and capabilities. It fails with the contracts `HostVerificationError` |
| `./loopback` | `LoopbackConnectionLive({directory})`: privileged `ConnectionService` for a daemon on this machine |

Remote hosts run the [daemon](../../apps/daemon/README.md#remote-host) in host mode, reached through the [SSH package](../ssh/README.md); its listener binds only `127.0.0.1`.

## Behavior worth knowing

- **Two sockets, one listener.** Chat, folders, control and provider setup (`ChatRpcs`, `LocalHostRpcs`, `ProviderSetupRpcs`) are served at `/v3/rpc`; the file host (`WorkspaceRpcs`) at `/v3/workspace`, so a large file never delays chat (D10). Both are Effect RPC groups from contracts on the one `Bun.serve`, routed by path, each with its own connections and limits; both client links (`rpc-link.ts`) share one connection per connection generation and socket, and send each request once.
- **Upgrade (D13).** An upgrade is authenticated before Bun accepts it: the client asks signed health for a nonce (single-use, 30 s, at most 64 outstanding across both sockets) and offers the socket's protocol (`moonbase.rpc.v3` or `moonbase.workspace.v3`) and `moonbase.proof.<nonce>.<hmac>`, an HMAC under the host key over the nonce, host and that protocol, so a proof opens only the socket it was made for. A wrong key, host, protocol binding or replayed nonce is 401, a missing or other protocol, another path, a query or a malformed handshake 400, a browser (`Origin`) 403, a `Host` other than `127.0.0.1:<any port>` (through an SSH forward it names the client's end of the tunnel) 400, and past 32 connections of that socket 503 (an accepted upgrade holds its place until it opens, so upgrades accepted together stay under the cap); every reconnect proves itself again. No message is read before an upgrade is authenticated. After it, a connection silent for 30 s is closed (clients ping every 5 s). Each connection writes one message at a time and waits while Bun buffers more than 1 MiB; a client that drains none of it for 20 s is cut, and while replies waiting to be written hold more than the socket's bound (16 MiB on `/v3/rpc`, 64 MiB on `/v3/workspace`) the daemon stops reading the connection (what the client sends meanwhile waits in its own and the kernel's buffers, and the idle close waits too, while the drain bound still applies).
- **RPC socket.** A message is at most 256 KiB and a connection runs at most 32 requests and 64 watches at once. Every request names its host at the top level (`{ host, input }`) and is served by generic handlers over the services (`rpc-handlers.ts`). Mutations and reads a caller may not abandon run to completion even if their connection drops; a handler's defect is answered `HostUnavailableError` (`failed`) with no diagnostics. The client caps inbound messages at 1 MiB (D11) and waits 20 s for a reply; a dropped or late mutation is `UncertainError`, never resent. Watches stream a value, then deltas where one pays (`watch-deltas.ts`); a resubscribe after a drop starts from a fresh value (`reset`), with no replay, takeover or coalescing (D10).
- **Workspace socket (`workspace-v2`).** Advertised and served only when the daemon composes a file host. A request or reply is at most 16 MiB of JSON (its message 16 MiB and 64 KiB): the client refuses a larger request unsent (`InvalidRequestError` `request-too-large`) and drops a larger message; the daemon refuses a larger reply before sending any of it (`reply-too-large`, or `UncertainError` for a mutation, which applied). Per connection the daemon runs at most 32 requests, 2 more `saveStatus`/`operationStatus` calls and 64 watches, holding at most 32 MiB of plain requests' input (estimated from its strings; status calls and watches are not charged, so they still run when it is full); past any of these a request is refused `HostUnavailableError` (`busy`) before it runs, so a refused mutation was never applied. Each request names its host, and each input's checkout (or chat) must be that host's (`Unauthorized` otherwise, checked by both sides). Reads are interrupted when their caller cancels or the connection drops; `isHostMutation` lists the mutations, which run to completion once started and are journalled by the host under their request ID: a repeat replays the first outcome, after `Unavailable`, `Cancelled` or `Persistence` the same ID runs again, and after `Uncertain` it is reported interrupted, so a client mints a new ID once the leftovers are inspected (`captureImports` is not journalled). Deadlines are the client's, by class (`hostDeadlineMs`): reads 20 s, lookup and search 30 s, mutations 60 s, worktree creation and `git init` 120 s; past one a read is cancelled and a mutation is `Uncertain`, which `saveStatus` or `operationStatus` resolves. `RemoteWorkspaceHostLive` keeps the daemon's places and its 32 MiB input bound itself (charging each request its encoded length; waiters are not served in order): a request waits up to its deadline for its place and bytes (`busy`, never sent, past it) and keeps them until the daemon answered or the connection closed, even after its caller gave up, so the status calls always have theirs and the daemon never refuses an honest client's request for its input. It refuses a reply naming a checkout of another host (`Incompatible`, or `Uncertain` for a mutation). The watch (`watchWorkspace {host, checkout}`) sends `{ready, revision, error?}` whole after each change; one the host ends is `HostUnavailableError` (`watch-ended`), so its client watches again, and a resubscribe after a drop starts from a fresh value, which `watch` delivers as an event to read again from (it ignores `paths`: the whole checkout is followed). A message counts only once it has all arrived, so a large reply delays the pong behind it: the client waits `workspacePingTimeoutMs` (158 s, the idle bound plus a 16 MiB reply at 128 KiB/s) for any message before dropping the connection. Below that rate a maximum-size reply drops it and makes the mutations in flight on it `Uncertain`; a read that large needs about 820 KiB/s anyway to meet its 20 s deadline.
- **Errors (D14).** Each procedure declares the error union of what it can fail with (contracts `chat-rpc`, `daemon-rpc`, `workspace-rpc`); a handler sends a service error its procedure's union names as its tag and fields (never a cause) and anything else as `HostUnavailableError`. A request for another host is `UnauthorizedError`, an operation health doesn't advertise `IncompatibleHostError` (`not-served`, refused before connecting). The client takes from a host only errors of those unions, decoded into its own classes, and presents them (D11): `presentRemoteError` and `presentWorkspaceError` replace the text a host could fill (an outcome's operation, Git's output, paths, a pattern's reason, a recorded refusal's text) with the client's own and drop an outcome's target. The client's own failures are `HostUnavailableError` (closed, refused, unreachable, busy, a lost read reply, a changed generation), `IncompatibleHostError` (not a daemon, not served, an invalid reply or update) and the connection's errors. Watch reconnect backoff (250, 500 and 1000 ms per outage, renewed after 5 s of values), deadlines and the idle close run on the Effect `Clock` (`TestClock` in tests).
- Signed health lists capabilities. Every host has `chat-v0` and `rpc-v1`. A server given `daemon` operations (the daemon, in either mode) adds `daemon-local-v1` (local-mode chats, `getActiveWork`, `markFolderAsProject`), `providers-v1` (provider setup) and `folders-v1` (`approveFolder`, `listRecentFolders`, `checkChatFolder`, `checkApprovedFolder`); a host-mode daemon adds `roots-v1` (`listHostFolders`), and one given a file host `workspace-v2`. The server serves only what it advertises, and the client checks the capability in signed health before sending: from a host without `daemon-local-v1`, `getChatHost`, `createChat` and every daemon operation are `Incompatible`, since every host must be a daemon. The protocol is version 3; protocol 1 hosts and clients are refused. Over SSH, OpenSSH provides transport encryption.
- Daemon operations are listed in explicit handler maps. Provider setup is scoped to an owner the client names (Electron uses its document id), so one owner never sees or answers another's flow; `releaseProviderOwner` ends an owner. The daemon mutations (`approveFolder`, `markFolderAsProject`, provider login, answer, cancel and logout) carry request IDs echoed in their replies: a lost or unproved reply is `Uncertain` and is never resent, and the server returns a recent request's outcome (keyed by owner and request ID) again rather than rerunning it. Only a refusal the daemon made before applying anything is forgotten, so it may be sent again.
- The daemon listens with `Bun.serve` (`serveChat` runs only under Bun; the client side runs on Node and in Electron too); `@effect/platform-bun` is not used, since the upgrade is authenticated before Bun accepts it. Bun does the WebSocket framing and refuses a message past the workspace bound from its header; each socket closes a connection whose message passes its own bound (1009). Accepted with the one listener: Bun's bound is the listener's, so it buffers an authenticated `/v3/rpc` message up to 16 MiB and 64 KiB before that socket's 256 KiB check closes it. The HTTP side answers at most 128 requests at once (more get `503`) and closes a connection idle for 10 s. Known limit, accepted: `Bun.serve` has no TCP connection cap or header deadline, and its idle timeout restarts with every byte, so a local process can hold many slowly trickling connections. The 128 in-flight request cap and each socket's caps still hold, and the listener binds only 127.0.0.1.
- `LoopbackConnectionLive` takes the expected host and store from the daemon's `identity.json` when it is built, and starts disconnected, so it builds while the daemon is stopped (without `identity.json` it fails `Unavailable`). On each connect it reads `identity.json`, `endpoint.json` and `token` again (private files in a private directory, never followed through links) and verifies signed health for that host and store. A connect that finds the same daemon process (the port and `pid` in `endpoint.json`) keeps its generation; a restarted or replaced one starts a new generation, even on the same port, and requests bound to the old one fail. It is privileged: its endpoint holds the token, so it never reaches a renderer.
- Each value is decoded once, where it arrives: the server decodes requests and the client replies (chat replies with `checkChatOutput` from `@moonbase/contracts/chat-validation`); the workspace client decodes its inputs before sending, so a request it could not encode is refused unsent. The services on either side, and `serveChat`'s configuration, are typed and trusted.

## Checks

```sh
bun run --cwd packages/daemon-protocol typecheck
bun run --cwd packages/daemon-protocol lint
bun run --cwd packages/daemon-protocol test
```

`test` runs under `bun test` against the real chat engine (`@moonbase/chat-runtime`, a dev dependency) with controlled providers and temporary stores. One case runs the compiled remote client in the pinned Electron, as desktop main runs it, which covers the client's Node path and that it bundles no engine. Workspace tests serve a controlled file host and drive `RemoteWorkspaceHostLive` against it, with a raw socket for a client that reads slowly. Host-process tests run a controlled local-mode host (`test/faux-host.mjs`) as a child process: crash recovery and parked work.
