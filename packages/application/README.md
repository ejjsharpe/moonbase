# Application

`@moonbase/application` holds the headless editor and chat features: controllers, shared command dispatch, cancellation, composition and lifecycle. It imports no Node, Electron, React or infrastructure implementation; callers inject clients and platform capabilities.

`createMoonbaseApplication` composes editor-only, chat-only or combined applications in one client runtime, with coordinated Quit (preservation, Save/Discard/Cancel prompts) and disposal. [`examples/headless.ts`](examples/headless.ts) runs all three compositions without Electron.

| Export | Purpose |
| --- | --- |
| `.` | Application factory, lifecycle snapshots and types |
| `chat` | Headless chat model and controller, including transcript navigation and Find |
| `editor` | Headless editor model and controller |
| `testing/memory-workspace` | In-memory workspace capability for tests and demos |
| `runtime/handlers` | Shared command dispatch and subscriptions |
| `runtime/clients` | Editor, chat and connection clients bound to an existing runtime |
| `runtime/effect-client` | Invocation and observation helpers bound to a supplied runtime |

The editor controller lists a checkout's project worktrees (`listWorktrees`) and creates one (`createWorktree`), opening and selecting the new checkout. `initializeRepository` runs `git init` in an open plain-folder checkout and moves its tabs, drafts and recents to the resulting Git checkout, as reopening a folder that became a repository elsewhere does; while it runs, the snapshot's `initializing` names the checkout and recovery publication waits. `reveal` expands a file's folders and selects it in its checkout's tree, resolving whether it did. It lists only levels not already listed and asks Git only about levels not yet classified: while the tree hides ignored files, an ignored file (or one in an ignored folder) turns that off, or with `{ ignored: 'skip' }` stays unrevealed. A newer reveal in the checkout cancels its remaining work; that, closing the checkout or its `current` callback returning false abandons it before the tree changes. With `{ quiet: true }` its failures reject without being reported. `setFollowActiveFile` saves the Follow Active File setting with the editor recovery; recovery saved before it existed reads as on. `createLookup` and `createTextSearch` give a popup its own debounced file-name and file-content queries; a newer query cancels the running one and any open from the popup, and earlier results stay until the new ones arrive. Repeating the last query is a refresh: it shows no search, leaves an open running and, while that query still runs, reruns it once it answers. A failed open's message stays until the next query or open, while refreshed rows still arrive. `runMutation` applies a `createMutation` file operation without a dialog: it calls the supplied `confirmReplace` only when existing entries would be replaced, returns `{ completed, error, items }` (the operation's per-entry outcomes, so a batch that failed partway says what it did) instead of throwing (even when `confirmReplace` does), and disposes the mutation once on every path (an aborted `signal` disposes it at once, without waiting for a pending confirmation). A move onto its own entry, which changes only its name's case or normalization, replaces nothing; a copy onto its own entry is refused. A batch import finds what it would replace from the `nativeNames` its action gives (such as dropped files' names), or else takes typed replacement paths; the workspace checks each replacement against the actual source names.

Renderers receive browser-safe clients. Native and transport adapters validate and authorize input before calling the shared handlers; schema validation alone grants no authority. A `ChatClient` that receives untrusted data decodes and size-bounds every reply and snapshot (the Pi runtime's local and remote services; desktop forwards them to the renderer unchanged); shared chat code trusts `ChatClient` outputs and checks only their meaning: echoed sources and selections, cursors, offsets, authority and liveness.

The transcript retains up to `transcriptLimits.summaryRecords` history records and `summaryBytes` of summaries (each entry's text is a 4 KiB preview). Earlier and later reads add a page and evict from the end the reader is moving away from, never the reading anchor's row; other growth (snapshots, part reads) evicts from the end farther from the anchor, or the oldest at the live edge. Evicting the newest records stops following. A reader follows while their saved anchor is null (or a live row) and history reaches the newest entry; a snapshot that skips past the records then replaces them, and a page read for the replaced records is dropped. Only history reads set `error`; manifest and part reads keep their failures on their own state. A jump replaces the records when its entry isn't retained, and either way bumps `dataset` so the list places it afresh, at its top; a jump to the saved anchor's entry while it isn't retained (Retry after a failed restore) keeps the saved offset. `rows` lists them with the live response for a virtualized list; a saved reading position (`TranscriptViewAnchor`) is `{key, offset}`: a row, normally the first visible one, and how far the viewport top is below that row's own top, so it holds however much history around the row a restore reads.

The chat list reads up to 16 pages, so an old chat that is active again is still listed; `reloadChats` lists again in the background through the pages on screen, at most 64 (keeping the last list, any error and any listed chat it did not reach; a call during a reload joins it, and `{ latest: true }` runs one more after it) and `markSeen` records the activity time you saw, saved with drafts. On the first listing every chat counts as seen. `groupChatsByActivity` sorts chats into Ready (ended since you last looked, or a Send that could not be confirmed, not one still in `dispatching`), Working, Idle (nothing new) and Settled (chats you settled, unless running or unconfirmed). `settle(target, settled)` settles or unsettles a chat on its host, updates the list and open snapshot from the reply; the list's watch then delivers it (without an open watch, it reloads the list). Once the host is verified the list follows `ChatClient.watchChatList`: each first page merges into the list on screen (keeping chats past it), and a page marked `reset`, or the first after a failed watch, reloads. A reload that read before a watch page landed re-applies that page, so its older rows never replace it. A retryable failure watches again after the transcript's backoff; after that, or after any other failure, `watchChats` (as a window becomes visible) or Refresh watches again. Nothing lists on a timer.

Provider setup follows `ProviderSetupClient.watch`, opened by `refresh` (at start locally, once a connected host is verified): once the watch delivers it is the state's source and command replies no longer replace it, so a sign-in's progress appears without polling; a watch that fails `Unavailable` (a restarted daemon, say) opens again after the transcript's backoff, and after that, or any other failure, on the next `refresh`, `login` or `answer`.

`setDraft` refuses a mention whose path the saved format rejects (`isChatMentionPath`) with an ordinary `error`. `storageError` is reserved for drafts that could not be stored; it blocks mutations and Quit for the controller's lifetime.

After a retryable (`Unavailable`) watch failure, the chat controller shows the last snapshot as reconnecting and re-watches the selected chat after each backoff in `transcriptLimits.watchRetryMs`. Recovery only reads. A failed watch delivers nothing more and is released at once. The attempt count resets only when the failed watch had stayed up for `transcriptLimits.watchHealthyMs` after its first snapshot. Once the attempts run out, or if the transcript had already failed, the transcript stays failed until Refresh or reopening the chat.

```sh
bun run --cwd packages/application typecheck

```
