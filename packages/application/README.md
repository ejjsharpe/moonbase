# Application

`@moonbase/application` holds the headless editor and chat features and their composition. It imports no Node, Electron, React or infrastructure implementation; the process root supplies the `WorkspaceService` (and chat capabilities) and runs everything on its one runtime.

## Layout

`src/editor/` and `src/chat/` hold the two features, each exported through its `index.ts`; `src/runtime/` composes them. Each concept gets its own folder with up to three files:

| File | Holds |
| --- | --- |
| `x.ts` | Pure functions for derived decisions: no services, no state |
| `x-service.ts` | The `Context.Service` and its scoped `Layer`, holding the concept's `SubscriptionRef` |
| `x-atoms.ts` | Atoms (`effect/reactivity`) over the service, for subscription and caching, with no domain logic |

The editor's concepts are `session` (its modes and owned work), `alerts`, `views` (the recovery layout), `buffers` (drafts and tabs), `discovery` (watches, listings, Git status, comparisons), `operations` (file operations until acknowledged), `recovery` (the outbox, keeping the store in step, references), `tabs`, `tree`, `mutation`, `saves`, `preservation` (Close, Reload, Quit, Reopen), `checkouts`, `lookup` and `text-search`. `editorLayer(options)` composes them over the `WorkspaceService`; `EditorLoader.load` loads recovery; `makeEditorAtoms(context)` gives views an `EditorSnapshot` atom and the popups' lookup and search atoms. Tests and headless consumers drive the services alone (see [`examples/headless.ts`](examples/headless.ts)). The chat controller predates this and moves to concept folders in #295.

`MoonbaseApplication.layer(options)` composes one optional editor (built beneath it, so it is released after) and one optional chat (`ChatHost`: a single capability or named targets, opened, switched and released one at a time): `start` loads the editor and opens the chat, `canUnload` and `prepareQuit` keep every draft first (Save/Discard/Cancel prompts for the editor), and `release` ends the chat before the root disposes the runtime. A closed chat's release blocks reopening until it ends. Chat opens, closes and switches only while the application is live. `makeApplicationAtoms` gives views its snapshot.

| Export | Purpose |
| --- | --- |
| `.` | `MoonbaseApplication`, `ChatHost`, application atoms and snapshot types |
| `chat` | Headless chat model and controller, including transcript navigation and Find |
| `editor` | The editor's services, `editorLayer`, atoms, snapshot and errors |
| `testing/faux-workspace` | In-memory `WorkspaceService` for tests and demos |
| `testing/faux-chat` | Controlled chat and connection capabilities for tests and the headless example |
| `chat/clients`, `chat/promises` | Legacy until CL-22 #295: chat, connection and provider setup Promise clients bound to a runtime, and the Effect-to-Promise bridge they and the chat controller use |

Editor actions fail with `EditorError` (a `reason` and its message) or the workspace's tagged errors; `describeEditorFailure` is the one place a failure becomes alert text, and a host's own text never reaches it. Alerts come from `EditorAlerts.report`: a string, which callers pass only for copy they wrote themselves, shows as it is.

`EditorCheckouts` lists a checkout's worktrees, creates one (opening and selecting it) and runs `git init` in a plain folder (`initializeRepository`), moving its tabs, drafts and recents to the resulting Git checkout, as reopening a folder that became a repository elsewhere does; while it runs, the snapshot's `initializing` names the checkout and recovery edits wait. `EditorTree.reveal` expands a file's folders and selects it, listing only levels not already listed and asking Git only about levels not yet classified: while the tree hides ignored files, an ignored file turns that off, or with `{ ignored: 'skip' }` stays unrevealed. A newer reveal in the checkout cancels the running one; that, closing the checkout or its `current` callback returning false abandons it. With `{ quiet: true }` its failures aren't reported. `setFollowActiveFile` saves Follow Active File with the recovery. A popup's lookup and text search (`EditorLookup.make`, `EditorTextSearch.make`, scoped to the popup) debounce their queries: a newer query cancels the running one and any open from the popup, earlier results stay until the new ones arrive, and a change a watch reports refreshes the last query, which leaves an open running and, while the query still runs, reruns it once it answers. A failed open's message stays until the next query or open. `EditorMutations.mutate(action, options)` runs one file operation at a time behind its gate (`admits`: ready, not preserving, no mutation running, the checkout open, and a move or copy of 1 to `maxMutationEntries` entries), asking through `replacePrompt` before it replaces existing entries; a dialog passes its own `id`, so applying again after a lost outcome resolves that operation rather than running it twice. A move onto its own entry, which changes only its name's case or normalization, replaces nothing; a copy onto its own entry is refused. A batch import finds what it would replace from the `nativeNames` its action gives, or else takes typed replacement paths.

The workspace's client recovery store is the only writer of recovery. The editor gives each tab a buffer ID and sends edits through the `WorkspaceService`: `openTab`, `closeTab` (with `discard` to drop a draft), `updateDraft` and `updateLayout`. Its outbox (`RecoveryOutbox`) sends them one at a time, in order, a moment after the last change; a buffer's newer text replaces text not yet sent, and `RecoverySync.flush` succeeds once everything made before it is committed. A failed edit stays queued and the snapshot's `recoveryFailed` stays true until a flush succeeds; `recoveryReady` is true only when nothing is unsent, no save is unsettled and every operation is acknowledged. Close, Reload and Quit's Discard send `closeTab` and wait for it. After a file operation, a save or a watch event the editor loads the recovery and follows the store's outline (`watchRecovery` streams it without text): moves re-path tabs, a copied draft opens as a tab, and unsent text of a buffer the store replaced is kept in a `(unsaved)` file beside it and reported; then it acknowledges the operation.

The editor watches each open checkout. A watch that fails `Unavailable` (a restarted daemon, say) is watched again on the shared watch-retry schedule (`watchRetrySchedule`: each backoff in `watchRetry.retryMs`, `watchRetryMs` overriding it, its length capping the attempts, renewed when the failed watch had stayed up for `watchRetry.healthyMs`), and listings and Git status are read again once it is up, since changes were missed; only a failure that cannot be retried, or the last attempt's, is reported. Closing the checkout or the editor ends the backoff.

The chat and provider setup handlers (`chat/chat-handlers.ts`, behind `makeChatClient`, `bindChatClient` and the provider setup clients) turn the services' tagged errors into the legacy `ApplicationError` with `toChatApplicationError`, so renderers keep the codes they read until CL-22 moves them to tags.

Renderers receive browser-safe clients. Native and transport adapters validate and authorize input before calling the shared handlers; schema validation alone grants no authority. A `ChatClient` that receives untrusted data decodes and size-bounds every reply and snapshot (the daemon protocol's remote services; desktop forwards them to the renderer unchanged); shared chat code trusts `ChatClient` outputs and checks only their meaning: echoed sources and selections, cursors, offsets, authority and liveness. The chat controller builds typed inputs and leaves decoding them to the boundary they cross.

The transcript's limits (`TranscriptLimits`, `defaultTranscriptLimits`; the chat dependencies' `transcriptLimits` replaces some) are one object every transcript reader takes. It retains up to `summaryRecords` history records and `summaryBytes` of summaries (each entry's text is a 4 KiB preview). Earlier and later reads add a page and evict from the end the reader is moving away from, never the reading anchor's row; other growth (snapshots, part reads) evicts from the end farther from the anchor, or the oldest at the live edge. Evicting the newest records stops following. A reader follows while their saved anchor is null (or a live row) and history reaches the newest entry; a snapshot that skips past the records then replaces them, and a page read for the replaced records is dropped. Only history reads set `error`; manifest and part reads keep their failures on their own state. A jump replaces the records when its entry isn't retained, and either way bumps `dataset` so the list places it afresh, at its top; a jump to the saved anchor's entry while it isn't retained (Retry after a failed restore) keeps the saved offset. `rows` lists them with the live response for a virtualized list; a saved reading position (`TranscriptViewAnchor`) is `{key, offset}`: a row, normally the first visible one, and how far the viewport top is below that row's own top, so it holds however much history around the row a restore reads.

Every chat host is a daemon, so each new chat names its folder and model: `create` and a new chat's first `send` take its `settings`, and the controller keeps them with the pending create. A host reached through a `connection` (a remote one) waits for an explicit Connect; one without (this machine's) is used at start.

The chat list reads up to 16 pages, so an old chat that is active again is still listed; `reloadChats` lists again in the background through the pages on screen, at most 64 (keeping the last list, any error and any listed chat it did not reach; a call during a reload joins it, and `{ latest: true }` runs one more after it) and `markSeen` records the activity time you saw, saved with drafts. On the first listing every chat counts as seen. `groupChatsByActivity` sorts chats into Ready (ended since you last looked, or a Send that could not be confirmed, not one still in `dispatching`), Working, Idle (nothing new) and Settled (chats you settled, unless running or unconfirmed). `settle(target, settled)` settles or unsettles a chat on its host, updates the list and open snapshot from the reply; the list's watch then delivers it (without an open watch, it reloads the list). Once the host is verified the list follows `ChatClient.watchChatList`, opened before the first listing so changes past the first page made while it reads are not missed (its pages wait for that listing, and the latest applies after it): each first page merges into the list on screen (keeping chats past it, replaced by their `changed` rows), and a page marked `reset`, one whose `dropped` count grew, or the first after a failed watch, reloads. A reload that read before a watch page landed re-applies that page, so its older rows do not replace it; a page the watch computed before that listing can still show briefly until the next one. A retryable failure watches again after the transcript's backoff; after that, or after any other failure, `watchChats` (as a window becomes visible) or Refresh watches again. Nothing lists on a timer.

Provider setup follows `ProviderSetupClient.watch`, opened by `refresh` (at start locally, once a connected host is verified): once the watch delivers it is the state's source and command replies no longer replace it, so a sign-in's progress appears without polling; a watch that fails `Unavailable` (a restarted daemon, say) opens again after the transcript's backoff, and after that, or any other failure, on the next `refresh`, `login` or `answer`.

`setDraft` refuses a mention whose path the saved format rejects (`isChatMentionPath`) with an ordinary `error`. `storageError` is reserved for drafts that could not be stored; it blocks mutations and Quit for the controller's lifetime.

After a retryable (`Unavailable`) watch failure, the chat controller shows the last snapshot as reconnecting and re-watches the selected chat after each backoff in `watchRetryMs`. Recovery only reads. A failed watch delivers nothing more and is released at once. The attempt count resets only when the failed watch had stayed up for `watchHealthyMs` after its first snapshot. Once the attempts run out, or if the transcript had already failed, the transcript stays failed until Refresh or reopening the chat.
