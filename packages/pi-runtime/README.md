# Pi runtime

`@moonbase/pi-runtime` implements the contracts `ChatService` on Pi Durable, which owns execution, transcripts and tasks. Layers create no runtime; process roots compose them.

| Export | Role |
| --- | --- |
| `.` | Fixed-settings `PiRuntimeLive(config)` (one folder and model for every chat; no process root serves it now), per-conversation `LocalPiRuntimeLive(config)`, privileged `LocalPiControl`, and `LocalHostLive(config)`: the contracts `LocalHostService` (folder approvals, chat folder checks, active work, mark as project) over `LocalPiControl` |
| `./local-models`, `./providers`, `./credentials` | Local provider catalog, provider sign-in and injected encrypted credential storage |
| `./claude-code` | Claude Pro/Max subscription through the user's Claude Code login ([pi-claude-code](https://github.com/earendil-works/pi-claude-code)) |
| `./folders` | `createFolderApprovals(file)`: approved working folders, re-checked by identity on use; `createRootFolders(roots, { reserved })`: a host-mode daemon's approved roots and the folders under them, refusing a root that holds or sits in a `reserved` path; `checkChatFolder(chatFolders, path)` |
| `./host-configuration` | `decodeDaemonSettings` for the daemon's `daemon.json` |
| `./server` | `serveChat(config, client, daemon?, capabilities?)`: authenticated loopback listener for the daemon in either mode; `serveChat`'s `socket` option (`{ sources }`: chat list and provider setup change notifications, and connection tracking) adds the WebSocket at `/v2/socket`; `makeDaemonClient(runtime)` binds its folder, control and provider setup services, and `localDaemonCapabilities` / `hostDaemonCapabilities` are what each mode advertises |
| `./remote` | `RemoteChatLive`, `RemoteLocalHostLive` and `RemoteProviderSetupLive({host, openUrl, sameMachine})`: client-side services over an injected `ConnectionService` |
| `./socket` | `connectDaemonSocket(endpoint)`: one authenticated WebSocket to a daemon that advertises `socket-v1`, for requests and subscriptions; no client uses it yet |
| `./loopback` | `LoopbackConnectionLive({directory})`: privileged `ConnectionService` for a daemon on this machine |

Remote hosts run the [daemon](../../apps/daemon/README.md#remote-host) in host mode, reached through the [SSH package](../ssh/README.md); its listener binds only `127.0.0.1`. **A working folder is tool context, not a filesystem sandbox.**

## Behavior worth knowing

- Both modes run on Node 26.13 or newer or exactly Bun 1.4.4; anything else, Electron included, is refused as `Incompatible` before the store opens. Bun is qualified exactly, so upgrading it is a deliberate change. SQLite goes through chord's `node:sqlite` adapter on every runtime.
- Mutations carry request IDs bound to their full input. A lost or unproved reply is `Uncertain`; callers retry with the original request rather than resending, and reconnects never resend.
- `listChats` gives each chat's `activity`: `running` while a submission owns it, else how its latest generation ended (`idle`, `stopped`, `failed`), with when it started or ended (or the chat's creation time if it never ran).
- A local `createChat` without `cwd` is a chat without a project: after `approveCreation` accepts it, the runtime makes it a new, empty, private folder under `chatFolders`, named for the day, the title's first words and a short id (`2026-11-08-tidy-the-composer-a1b2c3d4`), and lists it with `ownFolder: true`. It is refused when `chatFolders` is unset or sits inside a Git checkout, where the agent's Git commands would act on that repository. The runtime never deletes a chat's folder, so the agent's files stay until you remove them; it removes only an empty one it made for a request that made no chat. `LocalPiControl.markFolderAsProject` clears `ownFolder` once the host has opened that folder as a project.
- `settleChat` stores when a chat was settled in its metadata (`settledAt` in listings and snapshots) or clears it; repeating the current state commits nothing, and a new Send unsettles the chat.
- `findChatFiles` lists the chat's working folder on the host with ripgrep (`ripgrepExecutable`, else `rg` on PATH) or, without it, `git ls-files`, honouring ignore files and skipping dependencies. A listing runs in its own process group with a 10 s budget. Its budget or closing the runtime stops it: the whole group gets SIGTERM, then SIGKILL 2 s later, and the search or close waits for it to exit. Cancelling a search leaves the listing running, since other searches of that folder share it. A new chat may search only a fixed-settings host's folder, or one the daemon's `approveFolder` accepts: a folder a local client approved, or one in a host's approved roots. Mentions reach the agent as the `@path` text; the agent reads the files itself.
- Stop targets only the captured submission/task. Cancelling or disconnecting a client never stops remote work.
- Remote hosts stream snapshots over an authenticated channel; messages are HMAC-authenticated, and OpenSSH provides transport encryption.
- The protocol is version 2: requests, replies and stream frames are HMAC-SHA256 under the domains `moonbase-daemon-v1` and `moonbase-daemon-stream-v1`, and health under `moonbase-daemon-health-v1`. Protocol 1 hosts and clients are refused.
- Signed health lists capabilities. Every host has `chat-v0`. A server given `daemon` operations (the daemon, in either mode) adds `daemon-local-v1` (local-mode chats, `getActiveWork`, `markFolderAsProject`), `providers-v1` (provider setup) and `folders-v1` (`approveFolder`, `listRecentFolders`, `checkChatFolder`, `checkApprovedFolder`); a host-mode daemon adds `roots-v1` (`listHostFolders`). The server serves only operations whose capability it advertises. The client checks the capability in each challenge's signed health before sending, so nothing reaches a host that doesn't advertise what it needs: from such a host, `createChat` with `settings`, a `mode: 'local'` `getChatHost` reply and every daemon operation are `Incompatible`.
- Daemon operations are strictly decoded on both sides and listed in explicit handler maps; their inputs name the host, which the server checks. Provider setup is scoped to an owner the client names (Electron uses its document id), so one owner never sees or answers another's flow; `releaseProviderOwner` ends an owner. The mutations (`approveFolder`, `markFolderAsProject`, provider login, answer, cancel and logout) carry request IDs echoed in their replies: a lost or unproved reply is `Uncertain` and is never resent, and the server returns a recent request's outcome (keyed by owner and request ID) again rather than rerunning it. Only a refusal the daemon made before applying anything (`InvalidInput`, `Unauthorized`, `Incompatible` or `Conflict`) is forgotten, so it may be sent again. Over HTTP, provider setup state is polled; the WebSocket pushes it.
- The WebSocket (`/v2/socket`, on the same 127.0.0.1 listener) refuses an upgrade with an `Origin` header (any browser page) or a `Host` other than `127.0.0.1:<any port>` (through an SSH forward it names the client's end of the tunnel), and allows 32 authenticated connections plus 8 still waiting for their hello; a ninth waiting one closes the oldest, so held handshakes never lock a client out. The hello must arrive within 2 s and is the only frame accepted before it (a ping is refused); a wrong token, host or protocol, and any tampered, replayed, reordered, missing, reflected, unmasked, text, fragmented or oversized frame (over 256 KiB; 4 KiB before the hello; refused from its header) closes the connection with code 1008 and no reason. Requests run as over HTTP (same decoding, bounds, request memory and cancellable reads), at most 32 in flight and 64 replies or refusals waiting to be written; closing the connection cancels its reads but lets mutations finish, so a client retries with the original request ID, and the client fails a mutation whose reply was lost as `Uncertain` and never resends it.
- Subscriptions (64 per connection) number their updates. The server keeps only the latest unsent value of each and works out the update when it can write: a delta from what it last sent where one pays (the running response's appended text and replaced parts, chat-list rows, provider fields, at most 32 KiB), else a fresh snapshot, so a slow client gets fewer, coalesced updates and never a backlog. Replies go before updates, so streaming never holds up Send or Stop. While the socket holds 1 MiB the server stops writing and reading, pongs included; a client that reads nothing of it for 20 s is disconnected. Chat updates come from the chat watch, which is driven by Pi Durable's commit invalidation; the chat list is read again after commits that change conversations, tasks, metadata or a run's start or end (`LocalPiControl.subscribeChatList`), and provider setup after any flow or sign-in change (`ProviderSetupChanges`). A subscription outlives its connection for 60 s (64 in all) with its last 64 deltas (256 KiB, and 16 MiB across all subscriptions, the oldest subscriptions' going first): subscribing again with its ID and `afterSequence` replays the deltas after it, or resets with a snapshot when they are gone. Subscribing with an ID another connection holds takes it over, and the old connection gets a `Conflict` error update for it. Besides kept deltas, each subscription holds the value it last sent and at most one unsent value, each a snapshot of at most 256 KiB. Each side sends a heartbeat after 10 s without sending and closes after 30 s without receiving an authenticated message (WebSocket pings are answered but do not count); these are separate from request deadlines.
- A refused daemon operation's signed error may name a reason from `daemonErrorReasons` (`@moonbase/contracts/daemon`), such as Claude Code managing its own sign-in or a missing folder; the client shows its own fixed message for that reason and code, and a generic one otherwise, never the host's text.
- `ProviderSetupLive` runs one sign-in per provider: starting one cancels any other owner's running flow for that provider, so a client that restarted under a new owner takes over ChatGPT's callback. An owner unheard from for 30 minutes (`inactiveProviderOwnerMs`) loses its flow, at most 64 owners hold one (least recently used go first), and the 256 most recently released owners stay refused.
- `openProviderUrl` over the protocol returns the sign-in URL, checked against the providers' sign-in origins (`https://auth.openai.com`) by the daemon and again by the client, which opens it through its own `openUrl`; the daemon never opens a browser. `ProviderSetupLive` without `openUrl` (the daemon's) refuses `openProviderUrl`, and `ProviderSetupService.getProviderUrl` reads the link instead (reading it counts as the owner's use, like polling). ChatGPT's loopback callback (`127.0.0.1:1455`) runs in the daemon, so it finishes sign-in when the browser is on the daemon's machine; otherwise the user pastes the final redirect URL. `RemoteProviderSetupLive`'s `sameMachine` says which applies, and the pasted-code prompt says so.
- `LoopbackConnectionLive` takes the expected host and store from the daemon's `identity.json` when it is built, and starts disconnected, so it builds while the daemon is stopped (without `identity.json` it fails `Unavailable`). On each connect it reads `identity.json`, `endpoint.json` and `token` again (private files in a private directory, never followed through links) and verifies signed health for that host and store. A connect that finds the same daemon process (the port and `pid` in `endpoint.json`) keeps its generation; a restarted or replaced one starts a new generation, even on the same port, and requests bound to the old one fail. It is privileged: its endpoint holds the token, so it never reaches a renderer.
- A snapshot's running response carries its text parts whole (`truncated: false`) while its parts' text fits `chatLiveTextBytes` (64 KiB) in all, so the reply renders as it streams without content reads; past that, a part keeps its preview and is read. Stored entries' parts always carry previews. The history page in the snapshot gives way to the live text, oldest entries first, to stay within a frame.
- `./credentials` stores one encrypted file per provider through injected encryption, such as `createKeyEncryption(source)`: AES-256-GCM with a random nonce per write and the provider id authenticated, under a 256-bit key from one source. `createKeychainKeySource` keeps the key in a generic-password item (service `Moonbase daemon credentials`, account the `storeId`), written and read by `/usr/bin/security -i` with commands on stdin, never in arguments; it takes an explicit keychain file for tests. Like a 0600 key file, the item is readable by any process running as the same user, through `/usr/bin/security`. `createKeyFileSource` uses an explicit absolute key file for headless and remote hosts: base64 of 32 bytes (`openssl rand -base64 32`), a 0600 regular file owned by the user, not a symlink, in a folder no one else can write to. `createMemoryKeySource` is for tests. The first write creates the key, and concurrent reads and writes share one load or create, so a locked keychain prompts once; a locked keychain (`security` exit 36), a failing `security` or an unusable key file is `Unavailable`, and no other source is tried. A credential that can't be opened under the current key, such as after the key was removed, fails to read; signing in again replaces it and signing out removes it, while a locked keychain or a failed file check leaves it untouched. `MOONBASE_TEST_KEYCHAIN=1` enables the test that creates and deletes a temporary macOS keychain; CI sets it on its ephemeral macOS runner.
- `./claude-code` runs the local `claude` CLI, which owns sign-in; Moonbase stores no Claude credentials, and Pi still executes every tool. The library ships TypeScript source, so only bundles (the daemon's `daemon.mjs`) can load it, and they ship its `inert-mcp.mjs` beside them. It uses the built-in model list, not Claude Code's account catalog. Hosts close its warm workers with `closeClaudeCodeProcesses()`.
- `claude` is looked up on `PATH`, then in its install locations, and runs with its own directory and those locations on `PATH`, so an npm install's `env node` starts from Finder or a non-login shell. A status check that fails outright reaches provider setup as the provider's `problem` rather than reading as signed out.
- Claude Code runs in, and tells the model, its process's working directory: the library has no per-request cwd. Local-mode chats, which each have their own folder, state it in a `working-directory` prompt section instead.
- A dropped or stalled stream reconnects up to three times per outage; an authenticated frame arriving at least half a heartbeat interval after a connection's snapshot renews that budget.

## Checks

```sh
bun run --cwd packages/pi-runtime typecheck
bun run --cwd packages/pi-runtime lint
bun run --cwd packages/pi-runtime test
bun run test:chat-integration
```

`test` runs the suite under `node --test` (`test:node`) and then under `bun test` (`test:bun`). One case runs the compiled remote client in the pinned Electron, as desktop main runs it. Host-process tests run a controlled fixed-settings host (`test/faux-host.mjs`) as a child process: crash recovery, parked work, and a client refusing local-mode features from it. Tests use controlled providers and temporary SQLite stores, never real provider quota or SSH hosts.
